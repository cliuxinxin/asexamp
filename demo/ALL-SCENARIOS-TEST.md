# TCG v2.5.13 一次串测九个要点

这是一套待执行的人工验收步骤，不是实测结果。按顺序操作，同一个测试项目、两个会话即可覆盖九项需求。A 完成主流程；B 验证项目复用。模型措辞和生成条数可以不同，以范围、引用、版本及保存行为作为判断依据。

## 准备一次

- 使用 v2.5.13，连接你要演示的真实模型。
- 新建项目“串测·员工门户”，使用该项目的 Default Profile，选择 HITP 人工关键节点。
- A、B 打开同一服务地址，选同一个项目，但分别新建会话，不同时修改同一成果。两个浏览器窗口可模拟两位使用者；不同电脑各自运行的本地服务不会共享数据。
- 使用 ZIP 中 `demo/01-login-requirement.md` 与 `demo/02-login-change.md`。先只上传第一份，第二份留到第 5 步。
- 开始生成前，打开 Profile 的“用例 Excel 模板”，新增一列：字段 `tester_notes`，列标题“人工备注”，填写方式明确选“人工填写”，保存 Profile。后面用这列验证程序能保护人工内容。
- 记录本轮模型、Profile 名称和版本。给结果记录三个简称：R = 当前需求理解成果；S = 最终生成用例所使用的场景成果；C = 这套场景对应的用例成果。这里只是纸面简称，操作时使用页面实际 ID。

## 开始页与模板快速检查

在主流程前可用单独的空会话完成：

1. 开始页输入框居中、宽度适中、默认较矮；发送消息后对话和成果区域扩宽。并排结果面板可调宽度。
2. 点“学习模板”，检查具体提示词自动填入；自己改一个词再切换任务，确认不会覆盖已编辑草稿。
3. 上传 `demo/03-case-format.csv` 学习用例模板，应用到测试 Profile；核对列名和顺序。
4. 主流程生成场景后导出场景 Excel，再新建会话上传该 Excel 并选择“学习模板”。应识别场景模板，应用后用例模板列保持不变。返回主会话再导出一次，核对场景列配置生效。

## 连续操作与通过标准

| 步骤 | 操作位置与动作 | 通过标准 |
|---|---|---|
| 1 | A 上传初始需求，文件用途选“主要需求”；点“生成用例”，检查自动填入的提示词，再发送 | 提示词自动填入；进入人工确认流程，没有直接跳过所有确认节点 |
| 2 | A 在澄清区逐条采用建议，修改答案为“5 次错误、锁定 10 分钟、不允许人工解锁”，勾选“保存澄清到项目”，提交 | 每个实际提出的问题都有建议；采用后对应提示消失；提交后项目记忆能看到确认内容 |
| 3 | B 打开项目记忆，再在自己的会话选择“证据问答”，发送下面的共享验证问句 | B 能查看并复述已确认参数；回答有项目澄清依据；不需要在 B 再输入这些参数 |
| 4 | A 确认需求理解，停在“确认场景”。不切换任务，直接在聊天框发送第 4 步估算问句 | 有逐场景区间、理由、假设及合计；没有新增用例成果；场景版本和等待节点保持不变 |
| 5 | A 仍停在场景确认，点击“补充资料”；上传第二份变更，点击“应用补充，重新理解” | 原任务及原成果仍可查看；出现新的后继任务，使用原目标和新旧资料；理解结果包含“强制下线”和“越权拒绝” |
| 6 | A 在新的需求理解确认节点，编辑当前摘要并保存；确认后，在场景确认区编辑当前场景的一段描述再保存，最后确认生成 | 两种中间成果都能保存新版本；修改时不会自行越过确认节点；后续使用当前版本；原历史版本仍可查看 |
| 7 | A 等待用例生成与自动评审完成，展开用例步骤；记录 S、C 的实际 ID/版本和 C 的条数 | 能看到前置条件、操作步骤与逐步预期结果；阶段记录能区分生成草稿和评审后结果 |
| 8 | A 对一条用例添加人工测试标记；仅勾选这一条→“AI 微调”→预览→确认应用 | 预览时 C 不变；应用后 C 新增版本；目标用例 ID 与测试标记保留；其他用例逐字段不变 |
| 9 | A 通过阶段记录打开第 7 步的 S 最新版本，修改一个已有场景，再新增 SC-DEMO-GAP；保存 | S 新增版本，原始阶段快照不变；覆盖表能指出新增场景尚无用例，已有场景变化待同步 |
| 10 | A 仅勾选刚改的场景和 SC-DEMO-GAP→“同步关联用例”；明确选择 C，预览并应用 | 只改变这些场景的关联用例；SC-DEMO-GAP 从 0 条变成至少 1 条；其他场景的用例不变；已同步范围的过期提示消除 |
| 11 | A 选中 1 条干净、认可写法的用例→“保存为项目样例”→选择同一 Profile→“保存样例” | Profile 显示所选样例并新增版本；样例不带 refs、scenario_id 等原业务关联 |
| 12 | A 对当前 C 分别“解释选中用例”和“总结用例”；再用“证据问答”追问 | 说明对应当前打开的 C；重复提问也不把前次回答当作用例；C 条数和版本不变 |
| 13 | B 刷新页面，用同一 Profile 和同样资料发起一轮范围很小的生成；检查生成请求上下文 | 新任务使用已保存的项目澄清及 Profile 样例；不是仅仅“Profile 页面显示已保存” |

### 第 2 步：澄清答案

先点采用，验证提示是否收起，再在答案区改成下面这些确定结论。保留系统已经组织好的问题/回答结构，便于逐条对应：

```text
连续密码错误 5 次锁定账号。
锁定时长为 10 分钟。
本期不允许管理员人工解锁，只能等待锁定到期。
成功登录后，连续密码错误计数清零。
```

三个待定参数如果没有被提问，而直接被当成已知事实生成，应记录为需求澄清验收失败。问题可以合并，不要求固定问句或条数。建议有依据时显示依据，没有依据时应明确是建议假设。

### 第 3 步：B 验证项目澄清已被使用

选择“证据问答”，不要将本条消息保存为需求正文，发送：

```text
根据本项目已确认的澄清，员工登录连续失败多少次会锁定？
锁定多久？是否允许管理员人工解锁？请说明依据，不生成场景或用例。
```

预期为 5 次、10 分钟、不允许。若 B 只能在项目记忆里看到内容，模型回答却不知道这些结论，不能将“共享复用”判定通过。

### 第 4 步：不选择任务，直接聊天估算

操作前截图当前场景版本和等待确认状态。不要点击估算按钮，不用切换上一次“生成用例”任务。在聊天框直接发送：

```text
根据当前这些场景，估算需要多少条测试用例，分别给出数量范围和理由。
先不要生成用例。
```

估算结果应直接出现在聊天中。再发送：

```text
只估第二、第三个场景，不生成用例。
```

如果场景少于三个，改成实际存在的场景编号。核对表中只有指定场景，然后追问：

```text
那只算异常情况呢？
```

核对仍按刚才场景估算异常情况，没有转为生成。每次估算结束后核对：

- 仍需你点击确认场景，任务才会继续生成用例。
- 没有新的 case 成果，也没有调用用例生成阶段。
- 估算表合计等于逐行最小值/最大值之和。
- 不要求之后实际用例条数一定落在估算区间内；估算是建议，不是生成配额。

### 第 5、6 步：中途补资料与修改中间成果

第二份资料增加管理员强制下线及普通员工越权拒绝。若不使用附件，可在补充资料弹窗直接粘贴：

```text
新增管理员强制下线功能：管理员对已登录员工执行强制下线后，
该员工原会话立即失效，再访问受保护页面应跳转登录页。
普通员工没有强制下线他人的权限；越权请求被拒绝，目标员工会话不受影响。
其他已确认的锁定规则保持不变。
```

这一步有意重新理解新旧资料。不要继续用补资料前的场景成果做后续联动测试；后面选择后继任务实际用于生成 C 的 S。

在新的需求理解摘要末尾追加以下一句，保存后再确认：

```text
本轮重点验证失败计数、锁定、强制下线及越权拒绝。
```

在新的场景确认节点，对“登录失败计数”相关场景补充以下已有依据的要求：

```text
明确验证成功登录后失败计数清零，之后的密码错误从第一次失败开始计数。
```

保留实际场景 ID、refs 和 requirement_ids。若已有完全相同描述，可改为把上述要求拆成更清晰的表述，以便观察版本变化。

### 第 8 步：制造一个容易核对的局部修改

1. 从 C 选一条用例，记下实际 ID。在“编辑”表单的“人工备注”里填写“人工标记-A001，请保留”，保存。该字段是准备时已设为人工填写的 `tester_notes`。如果表单暂未显示，可在 JSON 视图给这条填写 `"tester_notes":"人工标记-A001，请保留"`，不要改其他条目。
2. 保存后记录 C 当前版本及全部用例数；“历史版本”保留了这份修改前基线。
3. 仅勾选该条用例，点击“AI 微调”，输入：

```text
只修改选中用例：在标题前加“【微调验收】”，并把操作步骤和对应预期写清楚。
保留用例 id、scenario_id、refs、tester_notes 和其他已有字段。
不新增或删除用例，不修改未选中的用例，不改变业务规则。
```

4. 先检查预览，再点确认应用。通过标准：条数不变、选中 ID 不变、标题出现标记、tester_notes 原样保留，未选中用例逐字段保持原样。
5. 可用两个历史版本的 JSON 对比核对。人工保护以生成时 Profile 的“人工填写”定义为准，不能只增加一个陌生字段就假定程序强制保护它。预览到应用之间不要保存其他修改，以免预览过期。

### 第 9 步：一次准备“场景变化”和“缺少用例”两种覆盖状态

在阶段记录点“打开最新版本并编辑”，进入 S 的最新成果后，再点“编辑”；不要在只读旧快照上操作：

1. 对一个已有“失败计数”场景，将标题加前缀“【场景修订】”。保留实际 ID 和引用；描述明确“4 次密码错误后输入正确密码仍可登录，登录成功清零计数”。该要求来自第 5 次才锁定及成功清零规则。
2. 切换“JSON · 全部字段”，复制同一成果中一条有依据的退出场景作为新的数组条目，再修改副本；新条目的 ID 为 `SC-DEMO-GAP`，标题为“退出后刷新受保护页面”。
3. 描述填写：“退出登录后，刷新先前打开的受保护页面，应回到登录页。”从同一份需求里已有的退出场景复制实际 refs 和 requirement_ids；不要填写本文不存在的虚构引用。
4. JSON 视图中只改该副本的 id、标题和描述，保持它实际的 refs、requirement_ids 以及数组其余条目不变；注意对象之间的逗号。
5. 保存前确认 SC-DEMO-GAP 在 S 中尚不存在。它是人为构造的覆盖验收条目，不用模型评审是否业务重复作为本次通过条件。
6. 保存后打开“查看需求 → 场景 → 用例覆盖”。选择 C 分支，记录新增场景关联用例数应为 0，变更场景应显示待同步。

### 第 10 步：同步前先核对目标

场景卡片只勾选第 9 步改动的两个场景，再点“同步关联用例”，选择第 7 步记录的 C。若出现多套用例成果，不要全选。

```text
只同步选中的两个场景。
已有场景的关联用例根据最新描述修正，保留稳定 id；为方便验收，
这些关联用例标题前加“【联动验收】”。
为 SC-DEMO-GAP 补充至少一条有有效需求引用的用例。
其他场景的用例保持完全不变，保留 tester_notes 及其他人工内容。
```

先看预览范围和新增 ID，再应用。不能只看“保存成功”：还要核对 C 的变化、SC-DEMO-GAP 是否有用例、未选中场景的用例是否原样保留，以及同一个 C 分支下的覆盖状态是否更新。若界面尚未刷新，可收起并重新打开覆盖表。

### 第 11、13 步：样例既要保存，也要验证进入下一次请求

- 选择不带人为验收标记、写法认可的一条正常用例固定到 Profile。
- 固定会替换这个 Profile 原有固定样例。打开 Profile，检查当前保存的内容和版本。
- B 刷新页面，确认选择的是同一 Profile。上传初始需求及变更资料后发起一个小范围任务：

```text
只针对“启用员工使用正确密码登录成功”设计少量用例。
使用当前 Profile 的格式和写法，保留需求引用；不要展开锁定、退出或强制下线场景。
```

- 进入用例生成阶段后，打开“执行过程→对应生成调用→查看发送内容→任务上下文”，确认 `format_samples` 或 `profile.sample_cases` 中有刚才固定的样例；同时可检查本轮使用的项目澄清。
- 检查生成内容遵循样例字段和写法，不要求逐字复制样例。样例里的业务内容不能替代当前任务的需求。

### 第 12 步：连续解释不应修改成果

先选中 1–2 条，点击“解释选中用例”，使用：

```text
向产品经理解释这些用例的测试目的、主要操作和预期结果。
说明它们验证了哪些业务规则。不要修改或新增用例。
```

然后取消选择，点击“总结用例”。最后保持 C 在结果面板中打开，选择“证据问答”再问：

```text
当前这些用例中，哪些覆盖账号锁定，哪些覆盖强制下线？请列出实际用例编号。
只解释已有内容，不修改结果。
```

三次操作前后 C 的版本与用例条数应保持不变；列出的 ID 应来自当前 C。
