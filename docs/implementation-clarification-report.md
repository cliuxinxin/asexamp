# v2.9 澄清提交与当前理解更新

已实现设计第 3、8 节中的当前任务澄清采用规则。

- `clarification.adopt` 使用 `submit:true` 时提交并立即更新需求理解；省略 `submit` 保留旧草稿接口。`draft_only:true` 明确只改草稿。
- `clarification.save` 提交后使用同一条有界 `artifact_modify` 能力更新理解，不再等用户另行继续。默认项目共享、适用范围、替代记录由项目事实模块统一保存；`status:provisional` 仅作为当前任务假设。
- 部分回答保留未答问题并刷新当前待确认版本。模型返回空问题列表也不能抹掉用户未答的问题。下一次提交保留前一轮已保存的项目事实。
- 全部回答后仅消费澄清输入节点，真实 LangGraph 停在 `strategy_review`。没有提交理解批准，不生成场景。
- 澄清编辑使用等待任务的独占令牌。模型调用期间不持有数据库事务；确认被拒绝；输入清单、控制版本、节点、编辑令牌和命令取消状态都在提交时复核。失败保留原理解和可重试的已提交答案。
- 刷新回执按需求成果与澄清来源去重。澄清节点重放复用已提交来源与当前理解，不再对同一答案调用模型。
- UI“采用此答案”直接提交；“先按假设使用”使用任务假设状态。统一主按钮为“提交答案并更新理解”，不再串联保存、共享、继续三个操作。
- 新任务默认聊天来源过滤历史 `provisional` 来源；用户显式选择来源仍遵循原入口。

验证：新增 `tests/test_clarification_flow_v290.py` 的真实 Store/LangGraph 定向回归先运行得到 3 失败、1 通过，然后实现。最终新增 6 项全部通过，覆盖立即更新、理解关停留、部分回答保留、草稿隔离、假设不共享、失败后复用来源重试，以及编辑期间确认拒绝/暂停后的晚到结果拒绝。`npm run build` 通过。

另运行既有需求刷新、项目事实和 v2.5 主流程测试。v2.6 旧草稿测试中“save_draft 默认不共享”断言与本轮已授权规则冲突，需要按 v2.9 更新；旧前端“采用仅 PATCH 草稿，再点保存/共享/继续”测试也描述被本轮替换的交互。
