## Important findings

1. **Historical explanations consume current source text.** `context_service.artifact_context` selects supplied/current evidence and constructs a fresh source manifest. It never resolves the source versions stored in the artifact's dependencies. `storage.evidence` only reads current chunks; `input_versions` preserves source bodies but not exact historical chunks/locations. Reproduction: create a scenario against source v1, update source and its referenced chunk to v2, explain the saved scenario. The pack contains old scenario text but v2 evidence and a v2 source manifest. **Fix:** preserve versioned chunks with source snapshots and resolve default historical explanation evidence from recorded source dependencies; explicitly requested current-source comparison must be a distinct mode. Do not silently substitute current content if historical spans cannot be recovered.

2. **A report/title annotation falsely refreshes business provenance.** `operations.revise_artifact` replaces dependencies with `deps.manifest(source_ids=sources)` whenever no explicit manifest is passed; `Store.annotate_artifact` cannot pass one. This also discards prior artifact/profile dependencies. Reproduction: change the source of a saved scenario; its status is `needs_review`. Rename that scenario through `annotate_artifact`; status becomes `current`, dependency source version advances to v2, and old business items remain unchanged. **Fix:** annotations preserve the previous business dependency manifest; normal revisions retain provenance of unchanged inputs and merge only explicitly consumed replacements. Keep commit-time freshness guards separate from persisted derivation provenance.

3. **`Store.put` can publish a head that has no immutable revision.** Its guard rejects older revisions and changes to an existing revision, but accepts any larger revision with arbitrary business changes. Reproduction: `store.put('artifact', {**saved, 'revision': 2, 'items': changed})` succeeds; `store.get` returns revision 2 while `store.revision(id, 2)` fails. The existing historical-context test actually creates this inconsistent state. **Fix:** restrict public `put` to operational metadata on an existing head; give the common commit boundary an internal atomic insert/head-update operation, or insert the new revision before validating and publishing its head within the same transaction. Adapt fixtures to create real revisions.

4. **Necessary business-rule closure is incomplete.** `rule_projection` recognizes an unconditional global rule only when provenance is exactly `global_rules`, so an entry under `requirement_map.global_rules` with refs outside the selected row is omitted. Separately, `artifact_context` projects rules once, then adds linked requirements without projecting their rules again: R1→R2 includes R2 but excludes a rule scoped only to R2 and its evidence. Both are concrete omissions of required business context; a generic partial flag does not make the input sufficient. **Fix:** determine global applicability by rule category, independent of storage path, and iterate requirement/rule expansion to a stable closure before evidence selection and budget admission. Preserve visible rejection if the necessary closure cannot fit.

5. **Historical provenance doubles as an impossible freshness guard.** Context packs retain exact ancestor versions, including multiple revisions of the same ancestor. `dependencies.assert_manifest` reconstructs every artifact ref from the current head, deduplicating them. Thus a pack using a valid historical ancestor can never pass a subsequent commit check once that ancestor head advances—even when only an unrelated parent item changed and `artifact_status` correctly reports the selected dependent item current. The focused per-item history and historical-manifest tests establish both sides, but never test modifying such a dependent artifact. **Fix:** retain historical consumed snapshots as provenance, and independently capture current head/item freshness guards at operation binding. At commit, validate those guards against changes since binding rather than require all historical provenance revisions to become current.

No concrete Important/Critical defect was found in the reviewed final-budget transport settings or header-secret redaction. Capacity counts are disclosed estimates, and server mode relies on an explicitly configured enforced output cap. No Critical findings.
