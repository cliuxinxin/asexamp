# 自动、人工与聊天的协作规则

这套系统有一条固定的成果流程：需求理解 → 场景 → 用例草稿 → AI 评审结果。聊天负责在这些阶段前后执行明确能力；LangGraph 保存阶段和等待位置；版本校验负责确认与保存是否仍针对当前输入。

## 两种模式，同一条主流程

| 已保存成果 | Human 的停留点 | 明确确认后的动作 | Auto |
|---|---|---|---|
| 需求理解、业务图与测试方案 | 确认需求理解 | 生成场景 | 自动进入场景 |
| 测试场景 | 确认测试场景 | 生成用例草稿 | 自动生成草稿 |
| 用例草稿 | 确认用例草稿 | 执行一次 AI 评审并保存优化结果 | 自动评审 |
| 评审结果与当前用例 | 确认评审结果 | 总结并完成本轮任务 | 自动完成 |

资料缺失或需要澄清时仍会单独提问。明确的“只到场景”“只生成，不评审”约束在两种模式都有效。界面选择的模式、范围和字段设置优先于模型推断，任务卡显示保存后的实际模式；运行中不能通过切换一个页面选项偷偷改变已有任务。

新任务采用上述四个确认点。旧版任务保留创建时的检查点与确认顺序，避免升级后插入意外审批或重跑已完成阶段。完整演示请新建对话和任务。

## 等待确认时，聊天能做什么

| 用户意图与说法 | 执行结果 | 主任务位置 |
|---|---|---|
| “这些场景需要多少用例？只估算。” | 给出逐场景范围、假设和理由，不创建用例 | 原位等待 |
| “解释第三条用例，列出步骤和预期。” | 基于指定版本解读，不修改成果 | 原位等待 |
| “看覆盖及未覆盖部分。” | 展示需求→场景→用例关系和过期状态 | 原位等待 |
| “微调选中场景并同步关联用例，先预览。” | 展示目标、差异和受影响条目 | 原位等待 |
| “应用这个预览，不继续。” | 原子保存新版本；保留未选中条目、人工字段；更新当前确认版本 | 原位等待 |
| “只看新附件的影响，不修改。” | 只读列出受影响需求、关联候选和引用 | 原位等待 |
| “按新附件更新受影响需求与场景。” | 更新明确范围，保留历史版本；下游状态可在覆盖表查看 | 原位等待 |
| “把第一条写法存为项目样例。” | 保存 Profile 格式样例，剔除业务引用身份 | 原位等待 |
| “导出当前场景和用例。” | 导出指定版本的 Excel | 原位等待 |
| “确认当前草稿，开始评审。” | 校验当前成果、版本与暂停节点后进入评审 | 进入下一阶段 |

用例评审分两种明确操作：“只读评审、给意见”是旁路问答；确认草稿后启动的主流程评审会保存优化结果。两者都展示真实步骤和预期，均不宣称测试已执行。

采用澄清建议只是填入可编辑草稿，建议随即收起；提交后才成为已确认的资料。默认保存到项目供同项目其他对话复用，可按界面选项取消共享。同项目的人需要访问同一服务、同一项目；本地独立安装的数据不会自动互通，当前没有成员账号与权限系统。

## 聊天如何控制流程

1. 对话图先读取轻量上下文：当前阶段、模式、成果目录与版本、当前选择、最近焦点、待处理预览。
2. 模型输出已注册能力组成的动作计划，例如“解释 → 预览修改”。模型负责理解语言，不自行编造接口或更改已明确的 UI 设置。
3. 服务端解析对象和条目范围，检查输入、权限范围、版本、暂停状态及停止目标。目标不明确时只问缺失信息。
4. 只读能力使用所需成果和相关证据；写能力通过预览/提交与命令回执保存版本；继续操作绑定具体确认节点、控制版本和成果 revision。
5. 新的停止要求会使旧的延后继续计划失效。修改完成本身不代表用户已同意进入下一阶段。

不同能力准备自己的上下文，并记录引用与容量。主任务按照容量分批，失败重试保持已接受批次的输入约束，不能拿新输入覆盖旧批次后声称是同一轮生成。上下文窗口应按实际模型服务配置。

## 本次失败如何处理

用户提供的 JSON 已通过解析，但这不能证明输入版本检查也通过。v2.7.1 修复内部展示/调度标记导致的摘要误变，并在小日志中记录具体依赖类别、ID、前后版本与摘要、变化字段，以及失败发生在模型前、模型返回后还是提交前。

仅凭旧小日志无法反推出本次究竟是哪项依赖变化，也不能补回未记录的信息。升级后可重试旧失败任务；如果确实修改过输入，普通重试仍会拒绝混合版本。应打开最新上游成果，在聊天中明确说“基于当前最新场景重新生成用例，采用人工逐步确认”，保留原任务和历史产物。

结构覆盖表示设计关系完整度，不等于测试执行通过；格式样例只指导字段与写法，不成为当前需求事实。
