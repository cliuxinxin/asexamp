# v2.9.2：上下文容量交给模型服务器

本版沿用 v2.9.1 的开始页、任务选项和聊天布局。升级后无需填写上下文窗口，也无需删除旧配置。

## 请求如何执行

1. 按当前阶段和选中范围准备输入，直接请求模型服务器。客户端不再用估算 Token 或固定字符预算拒绝请求，也不据此提前拆分业务批次。
2. 服务器正常返回，就继续原流程。
3. 只有服务器明确返回上下文超限，才拆分失败的业务批次，或减少对话调度中的历史与目录预览后重试。
4. 已完成的主流程批次和分页结果保留，重试从失败部分处理。原有需求理解、场景、用例草稿和评审结果的人工确认继续有效。

Token 估算仍可用于诊断，不参与发送准入。鉴权错误、普通请求体过大、模型输出被截断等错误分别处理，不会全部当成上下文超限重试。

## 设置变化

- “模型与设置 → 模型连接”显示上下文容量由服务器控制，不再提供窗口数值输入。
- 旧 `TCG_MODEL_CONTEXT_TOKENS` 和 `TCG_CONTEXT_CHARS` 不再用于拒绝请求。
- Ollama 请求不再传入 `num_ctx`，使用服务端配置。
- 单次输出预留及服务端输出策略保持独立，默认输出预留仍为 8192。输入超限和生成答案达到输出上限是不同错误。

## 超限后能自动处理的范围

需求理解、场景生成、用例生成、评审和模板字段补全会按完整业务条目拆分；场景关联修复与需求关系归并采用相同的服务器拒绝后拆分策略。对话中的估算、解释、评审、修改及新资料影响分析也会按可独立处理的范围拆分。

修改仍先形成完整修改建议，所有分组成功且校验通过后才允许应用。某个分组失败时，不会把前面分组的修改直接写入正式成果。

业务原文片段、当前用户指令、选中对象和人工确认约束不会为了塞进容量而被任意截断。普通聊天可以在服务器拒绝后缩小历史或目录预览，并标明预览不完整；缺少对象信息时仍需查找或澄清。

以下情况会明确提示处理方式，并保留已有成果：

- 单个业务条目及其必要证据仍超限，需要将该条目的来源按业务规则拆开，或使用更大容量的模型。
- 整份模板或跨版本比较超限，无法保证拆分后语义一致，需要按完整工作表拆分模板或减少比较版本。
- 同一场景的用例评审被拆成多个批次后，原有覆盖校验仍保留，可能拒绝删除一个批次内该场景的全部用例。

分批解释的最终汇总若仍超限，会直接展示各批已校验的完整解释和覆盖说明，避免丢失已生成内容。

## 快速验证

1. 保留原 `data` 和模型配置，停止旧服务，运行新版 `python3 start.py`，刷新浏览器。
2. 在模型连接设置中确认没有上下文窗口输入。旧配置中的 32768 不再是请求限制。
3. 新建会话，上传资料并生成用例。Human 仍逐阶段等待确认，Auto 连续执行。
4. 使用会明确拒绝超长上下文的模型服务提交较大输入：查看执行记录中的服务器超限与拆分记录；完成后确认每个输入仍有对应成果。
5. 在确认节点通过聊天估算、解释或修改选中条目，确认操作完成后仍处于该确认节点。

本版集成验证为后端 47 项、前端 11 项定向测试通过，TypeScript 与生产构建通过。未运行全部历史测试。

验证采用受控服务器错误和模型响应，覆盖真实 HTTP 传输、SQLite、LangGraph、保存与重试，以及设置和聊天输入交互。尚未连接你的内网模型；当前环境未完成浏览器视觉验收，聊天布局没有本次改动。
