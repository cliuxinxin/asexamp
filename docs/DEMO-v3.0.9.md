# v3.0.9：失败自动修复与生成内容保留

## 实际使用

1. 用原数据目录启动新版，完成模型连接测试。保留当前对话布局和任务选项。
2. 上传需求，在对话中发送“根据需求生成测试用例”。自动和逐步确认继续使用原来的主流程。
3. 如果模型结果出现覆盖漏项、字段格式或无效引用，系统自动发起修复。输入框上方显示真实阶段和“第 N / 3 次自动修复”。每次模型请求携带具体校验原因、缺失编号及上一轮结果。
4. 任一修复通过后，按照当前模式继续：自动模式继续处理；人工模式仍经过原有确认节点。没有错误时不会额外调用三次模型。
5. 三次修复后仍不合格，对话中出现“待核对草稿 → 查看已生成内容”。打开后可查看需求/场景/用例表格、步骤与预期、剩余问题、各次完整返回；拆批前已通过的内容也可直接查看。可下载 JSON 生成记录。
6. 返回对话，可说明需求或资料变更，或回复“重试当前步骤”。显式重试开启新一轮额度，并携带上次错误和候选内容；不会把旧失败内容当成成功缓存。旧草稿仍能从历史消息打开。

草稿是未通过校验的生成内容，不能作为已验证成果直接确认或混入正常 Excel 导出。页面不会同时显示“失败”和“等待确认”，也不会把覆盖漏项统一解释为连接故障。

## 修复规则

- **首次请求 + 最多 3 次修复，共最多 4 次内容请求。** Schema、引用修正和业务覆盖检查共用这一额度，不叠加内层重试。
- 引用修复保留完整用例；仅含引用的工具补丁保存在历史中，不取代标题、步骤和预期。
- 不凭空编造需求、清空引用或删除条目来假装通过校验。
- 连接、认证、权限、取消、依赖版本变化等错误需要对应处理，不反复让模型修改业务内容。
- 每个可拆分批次独立使用额度；已通过批次缓存可复用。进程恢复沿用原轮额度，并先校验已保存的返回；用户明确重试才开启新轮。
- 新逻辑适用于升级后发生的请求；旧版没有归档的失败响应无法追溯补出。

## 开发者稳定复测

真实模型不保证每次触发相同错误，可用定向测试验证失败路径：

```bash
PYTHONPATH=backend python -m pytest -q tests/test_generation_repair_v309.py tests/test_generation_candidates_v309.py tests/test_control_receipts_v309.py
```

覆盖两条需求但模型只返回一个场景的情况：确认最多 4 次调用、修复请求含缺失需求编号、仍失败则生成可读取草稿、不调用用例生成。另验证 schema 与引用共用预算、损坏原文保留、重启不多发一次请求、跨任务读取拒绝、后续阶段失败不显示旧阶段草稿。

前端 `generation-candidate-v309.test.tsx` 验证失败状态、三次修复计数、畸形字段安全显示、已完成批次表格和生成记录。浏览器真实视觉验收及你的内网模型验证仍需在部署环境完成。
