# v2.0.7 诊断与升级

## v2.0.7：创建环境停在 ensurepip，activate 不存在

用户日志在 Python 3.13 的 venv._setup_pip → ensurepip 阶段出现 ^C 和 KeyboardInterrupt，表明初始化被手动中断。旧启动器使用 EnvBuilder(with_pip=True)，pip 初始化先于激活脚本生成，并通过捕获子进程输出等待完成；因此在该阶段中断会留下 Python 已存在、activate/pip 可能不完整的环境。仅凭这段日志不能判断中断前是否真的卡死、等待了多久，或是否存在其他 Python 安装问题。

旧启动器只判断 .venv/bin/python 是否存在，会误把上述状态当成完整环境。v2.0.7 会检查 Python、pyvenv.cfg、activate，并实际执行 pip --version。需要补全时使用 with_pip=False 先创建环境骨架，再单独运行 ensurepip --upgrade --default-pip -v；pip 的输出直接显示到终端。初始化中断会提示重新运行命令。保留已有目录，不使用 --clear，也不删除 data 或 .env；环境修复后重新检查/安装应用依赖。

Python 的 ensurepip 使用随解释器附带的安装包，本身不联网；随后安装 requirements.txt 才需要网络。[Python ensurepip 文档](https://docs.python.org/3.13/library/ensurepip.html)。本次验证在 Linux/Python 3.12 完成，没有在用户 Mac/Python 3.13 上实测。

推荐取出新版包中的 start.py 替换原文件，然后在原项目目录重新运行 python3 start.py。无需 source activate。如果暂不替换启动器，也可逐条恢复：

```bash
cd /Users/liuxinxin/Documents/GitHub/tcg-case-agent-local
python3 -m venv --without-pip .venv
.venv/bin/python -u -m ensurepip --upgrade --default-pip -v
python3 start.py
```

每条命令成功后再执行下一条；若失败，保留终端的完整输出。不要删除业务 data 目录。

终端启动时的 .zshrc:source:4 是另一件事：该行引用的 OpenClaw 补全脚本已不存在。在 open -e ~/.zshrc 打开的文件中，将原 source 行改为存在时才加载：

```zsh
if [[ -f "$HOME/.openclaw/completions/openclaw.zsh" ]]; then
  source "$HOME/.openclaw/completions/openclaw.zsh"
fi
```

此修改只处理终端补全脚本的加载，不会安装或卸载 OpenClaw。

## v2.0.6：60 分钟等待与输入核查

诊断 run_e5a605a92b3e4884b789c6a7503b0df0 来自 v2.0.5：需求分析约 71 秒成功返回 35 条，澄清后分析首次 120 秒超时、重试约 100 秒成功；场景生成两次都在约 120 秒触发本应用的总时限。日志没有提供商 HTTP 状态码，不能据此认定提供商返回 504，也无法区分一直缓慢输出与上游中途停住。

按本次要求，本版把全部模型调用超时统一为 3600 秒，包括总时限与 HTTP 连接/读/写/连接池等待；连接测试和每次重试同样适用。旧配置中的 120/300/600 秒自动按 3600 秒执行，原文件和密钥不会被改写。启动后“模型与设置”应显示 3600 秒及固定 60 分钟策略，诊断 model.start.timeout_seconds 也应为 3600。仍需重启到新版代码，仅刷新旧服务网页不能改变后端。

在原失败卡片点击“重试此阶段”，会继续场景节点，不重新上传需求或重复已成功的分析。每次新的调用旁可点击“查看发送内容”，核查系统提示、证据、历史消息、Profile、澄清/修正信息和请求参数，也可下载 JSON。快照在发送前保存，不能证明远程服务收到请求；旧版本调用无法补回。API Key 与认证头不进入快照，普通诊断下载仍不含正文。

如果较早返回错误，请查看提供方状态码或代理日志；应用的 60 分钟策略不能覆盖外部服务自己的时限。有限重试保持不变，两次各等待 60 分钟时，一个阶段可能接近两小时；你可以随时停止。

## v2.0.5：直接看执行过程和 AI 返回

聊天中的“执行过程”默认展开，按时间显示阶段、批次和模型调用。每次调用的正文实时追加到自己的输出卡片，显示请求次数、耗时和校验状态；重试保留此前输出。完成后可在助手消息下方展开完整记录。

- 只有“等待模型返回内容”：请求已经开始，但尚未收到可展示的正文；模型可能排队或先处理输入，10 秒心跳会更新等待时间。独立 reasoning/thinking 字段不会展示。

- 连接测试成功但生成失败：测试是非流式小请求，当前生成要求模型服务支持流式 JSON；查看诊断中的提供商状态码和模型适配错误，并确认所配接口支持 stream=true。

SSE 不改变 LangGraph 的多轮会话和检查点机制，也不替代实际字段校验。升级前已发生的输出无法补录；服务重启后，未完成模型请求可能重新执行，并显示为一次新调用。

本版会自动迁移旧 events 表，增加事件类型。模型正文现在保存在本地 tcg.sqlite3 执行事件中；诊断下载和终端日志仍只包含元数据。执行历史目前没有自动清理上限。

## 这次修改解决什么

旧版终端主要是 Uvicorn HTTP 访问日志。重复的 `GET /api/chats/... 200` 只说明页面还能查询后端，无法证明模型请求成功或任务正在前进。`POST /api/settings/test 200` 也只是 HTTP 成功，测试结果应看响应中的 `ok` 或界面提示。

旧版前端未映射 `requirement_analysis`、`scenario_generation`、`case_generation` 等真实阶段名，会退回“正在处理”。v2.0.1 已补齐这些名称，增加批次、请求等待时间、重试次数及运行详情。

原始 TCG PRD 在当前解析方式下有 22,822 字符、476 个证据段，需求分析分 6 批顺序执行。模型每批都要读取上下文并输出结果，不能用一次连接测试的耗时估算整份文档。当时默认每次模型请求超时 120 秒，失败最多重试一次；这不是整个任务的总时限。这是旧版诊断阶段的背景；本次新诊断中直接失败的是 route 请求超时，详见本页开头。

2. 备份整个旧 `data` 目录。模型配置、密钥、上传原件、聊天数据库和图检查点需要一起保留。
3. 将新版 ZIP 解压到另一个目录，避免覆盖自己的改动。
4. 在新版项目目录执行以下命令，让新版继续使用原数据目录（Mac 示例）：

```bash

```

浏览器刷新页面，查看任务的“执行过程”，需要排查时展开“运行详情”。若仍显示旧版界面，强制刷新。`GET /api/health` 应返回 `version: "2.0.7"`。

## 查看日志

正常启动已开启 INFO 业务日志，无需额外参数：

```bash

```

```bash

```

需要 Uvicorn 原始访问日志时额外加 `--access-log`。使用自定义数据目录时继续带上 `--data-dir`。

Mac / Linux 可在另一个终端实时查看：

```bash
tail -f /Users/liuxinxin/Documents/GitHub/tcg-case-agent-local/data/logs/tcg.log
```

任务卡片“运行详情 → 下载诊断日志”会下载当前任务最近 200 条诊断事件；已完成的助手消息下方也有本轮日志下载入口。数据库每个任务最多保留 500 条诊断事件。诊断元数据包括模型标识、端点主机、任务 ID、节点、批次、请求耗时、异常类型及栈位置；不记录完整需求、聊天正文、提示词、模型响应正文、API Key 或请求头。

## 如何根据事件定位

| 最后出现的事件 | 含义与检查方向 |
| --- | --- |
| `run.scheduled`，没有 `run.started` | 任务已提交，执行器尚未开始；查看下载中的 `runtime.task_active` 和随后启动日志 |
| `checkpoint.loading`，没有 `checkpoint.loaded` | 正在读取本地图检查点，尚未进入业务节点 |
| `node.start` / `stage.changed` | 已进入具体节点；后续应出现模型请求、节点完成或错误 |
| `model.start`，没有 `model.transport_start` | 模型适配器尚未开始传输，检查随后的初始化错误；测试注入模型不会出现 transport 事件 |
| `model.transport_start` + 周期性 `model.waiting` | 已调用 LangChain 模型客户端，尚未拿到完整响应；查看模型服务端日志、负载和上下文处理速度 |
| `model.transport_response` | 模型已返回；字段包含响应字符数、可用的 Token 统计、结束原因 |
| `model.invalid_json` | 响应不能解析为 JSON；需要检查模型的结构化输出能力 |
| `model.transport_error` / `model.error` | 查看 `error_types`、`http_status` 和安全栈位置；401/403 通常与鉴权有关，404 可能是路径或模型名，400 可能是请求参数不兼容 |
| `model.retry` | 上一次请求失败，准备有限次数重试 |
| `node.error`，但模型已 complete | 模型调用结束，后续结构/证据/版本校验或写入失败，查看页面错误及节点位置 |
| `node.complete`，然后 `graph.returned` | 该节点/本次图调用已结束；随后应有等待或完成状态 |
| `node.interrupted` / `run.waiting` | 正常的人工暂停，需要回答或确认 |
| `run.completed` | 后端任务完成；若界面仍等待，刷新并核对同一 run_id |

HTTP 中间件生成 `X-Request-ID` 用于定位请求。模型调用以 `run_id + chat_id + node + call_key + attempt` 关联。同一请求重试不会混入其他聊天的日志。

## 多轮对话如何工作

- `chat_id` 对应长期聊天容器，保存消息、来源和产物。
- 每次普通发送产生一个新 `run_id`。LangGraph 使用该 run_id 作为 `thread_id`，隔离每轮的工作流检查点。
- 新任务读取该聊天最近 12 条消息（包含本次消息）、当前来源、所选 Profile，以及适用的已有产物快照。v2.0.1 显式按时间排序历史；诊断文件说明用了多少条、遗漏了多少条。
- HITP 回答通过 resume 继续原 run，场景确认时使用已编辑的最新场景。
- 同一聊天有活跃任务时不能普通发送下一轮；可等待、停止，或在 HITP 的指定入口继续。不同聊天可以各自运行。
- 超过窗口的原始消息仍在数据库里，但不会自动全部传给模型。目前没有长期摘要、语义检索或跨聊天记忆。
- 修改早期特定产物时，用该卡片的“让 AI 修改此结果”明确指定对象。普通自动路由默认携带最近的可见产物，不会把所有历史产物正文全部加载给模型。
- 需要长期作为业务依据的补充信息，应上传/粘贴到来源，或勾选“这条消息是需求正文”；普通聊天指令不会自动升格成业务证据。

这种分工支持多轮任务对话。它保留了每轮独立恢复和审计的能力，但不等同于无限上下文的自由聊天。直接把所有任务的 `thread_id` 改成 `chat_id` 会改变检查点和终态复用语义，不能单独替换这一行就当作记忆升级。
