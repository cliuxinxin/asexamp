# v2.5.4：自动过程、模板定义和本次日志问题

## 自动过程为什么不见了

此前自动流程只调用最终 publish；中间需求理解、场景和用例草稿存在数据库中，但未发布为聊天消息。完成后的 RunTimeline 又默认折叠，因此用户看到的主要是最终用例。

本版在自动模式的 understand、scenarios、cases、review 完成后，逐阶段发布摘要和成果入口。摘要使用现有模型产物的 summary 或标题，评审使用实际评审摘要；不增加模型调用和人工暂停。每个入口引用当时保存的 revision，生成时的草稿不会变成评审后的版本。阶段消息使用固定缓存键保证重试不重复发布。完成后调用过程默认展开，模型原文仍可单独折叠。

旧任务的执行记录仍能回看；未发布过的历史阶段消息不会凭空补造。

## 模板到底在哪生效

旧版将当前 Profile 传给生成和评审，Excel 导出也采用产物保存的 Profile 快照；但生成链路筛选业务证据时排除了 example，上传模板的正文没有在独立格式上下文中传给生成。仅上传模板不代表其中的定义已采用。与此同时，需求理解阶段收到全部 Profile，包含用例写作和 Excel 格式，增加了阶段混用的可能性。

本版：

- 需求理解接收输出语言、范围、场景深度、业务关注点，不接收 Excel 列映射。系统提示明确只输出需求规则，不能返回用例 steps/expected/preconditions/scenario_id；出现这些字段先定向修复，再生成场景。
- 生成和评审接收完整 Profile，包含 template_rules、excel_columns 及每列 definition；本轮选定的 example 正文通过 format_references 传入，仅作格式参考，不作为业务事实或 refs。
- Profile 界面新增每列“字段定义”；模板学习也可返回该定义。用例结果上的“本轮模板与字段定义”列出实际发送的配置、参考文件和导出列。
- steps 内部仍是 action/expected 对象数组。Excel 中 steps/expected 两列由导出器分别格式化，不要求模型为模仿单元格格式破坏内部结构。
- 导出仍采用保存的 Profile 列顺序、列名、Sheet 和布局。上传样例不会自动覆盖 Profile；更换导出列可学习模板并应用建议，或直接编辑映射。当前导出不保证复制原 Excel 的复杂样式、公式或合并单元格。

“已提供给模型”不等于已验证模型完全遵守每项自然语言定义。可在结果中检查具体内容；本地验证确认了输入传递和导出行为。

## 两段日志的解读

### 需求理解

日志显示错误位置等于原文末尾（position=10627），服务结束原因为 stop，但这不保证 JSON 结构完整。开头又包含测试用例字段和 TC 编号，说明当前阶段输出混入了用例格式。用户提供的是节选，不能对完整原文逐字复现。

本版对正常 stop、已有嵌套值完整、仅在文本末尾缺少结束括号的结构做有限修复：扫描引号及括号栈，只附加缺少的容器结束符，并重新解析；不修改任何已返回值。原始输出保留，事件 model.json_local_repair 记录补齐内容。未结束的字符串、数值、字段值、错误位置不在末尾等情况继续走模型格式修复，不能猜测补全业务内容。修复语法后仍进行正常字段和引用校验。

### 用例评审

粘贴的评审 JSON 本身合法，日志又没有终止错误，单凭它不能断言当时的具体拒绝原因。

代码中存在可复现的覆盖规则冲突：评审允许 delete，覆盖校验却要求所有输入场景始终至少保留一个用例。如果前面错误地把范围排除项生成成场景，AI 删除其唯一用例就会触发 lost_scenario_coverage。

本版允许 report.scenario_exclusions:[{scenario_id,reason,refs}] 表示有需求依据的范围排除。ID 必须属于丢失覆盖的场景、理由非空、引用来自本轮有效非模板需求。范围内的覆盖缺失仍要修正，虚构引用不能放行。排除项显示在评审结果中，原场景和用例历史保留；引用的语义正确性仍需业务复核。

### 小日志漏掉校验错误

模型调用退出时，其 call_id 绑定已结束，后续 batch.validation_failed 原先只有节点信息；小日志按 call_id 过滤，漏掉了真正的业务校验错误。

现在缓存调用标识并将校验事件关联到具体 call_id/call_key；小日志首先展示该次调用的字段或业务校验结论，再展示原始返回。任务运行中、自动修复后完成，都能查看之前那次拒绝原因。旧记录可根据节点和时间区间关联。日志中的“原始返回较长”仅说明日志节选，不能拿它断言模型输出未截断。
