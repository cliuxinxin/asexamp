# 统一工作区 · v3.0.14

## 使用方式

1. 从聊天里的成果卡片或修改建议打开全屏工作区。需求条目、测试场景和测试用例使用同一个入口。
2. 当前成果可双击单元格（或按 F2）编辑；通过工具栏新增、删除条目。测试步骤与预期结果成对修改。
3. AI 建议直接显示红绿差异。逐格接受或拒绝，也可继续手动编辑；决定完成后保存。只改变报告或列配置的建议也可点击“拒绝此建议”。本地已有未保存修改时，先保存或撤销草稿；保存前不会覆盖正式成果。
4. 选中条目后，在右侧 AI 助手输入修改要求。新的建议仍在当前表格内查看和确认。本地未保存修改会受到保护，需要先保存或撤销再让 AI 修改。
5. 查看历史版本时只能阅读和导出；需要修改时打开当前版本。旧提案、过期版本或执行中的成果也会限制保存，避免覆盖新内容。

## 保存与版本

统一接口为 `/api/artifacts/{id}/workspace-grid`：

| 方法与后缀 | 用途 |
|---|---|
| GET | 读取列、原始行、建议行、版本和当前模式 |
| POST `/project` | 将本地草稿投影为表格，不发布成果 |
| POST `/export` | 导出当前草稿或指定历史版本 |
| POST `/save` | 校验绑定、保存手动修改或提交 AI 建议决策 |

保存必须携带 `expected_revision` 与 `client_request_id`，有提案时同时携带提案和确认点标识。`proposal_decision` 默认为 `resolve`；明确拒绝整份建议时使用 `reject`，同样校验绑定与重复请求。绑定了 Profile 时也检查其版本。同一请求重复提交返回保存回执；过期版本返回冲突，不覆盖他人的更改。人工输入仍被记录为来源依据；新增独立场景、用例不会虚构上游需求。

历史工作区默认使用该成果版本保存时的 Profile，后续模板修改不会改变同一历史版本的列内容。拒绝建议不会生成新的成果版本；重启后重试拒绝仍保持拒绝，依赖接受该修改的后续任务不会继续执行。

Human 流程中的评审保存仍通过原生 LangGraph 确认点完成；自动流程继续使用原来的自动评审规则。Supervisor 后续导出等待保存完成后继续。

## 架构与清理

- `ArtifactWorkspace.tsx` 接管只读、人工编辑和 AI 协作；`table-review-model.ts` 根据列定义关联单元格与修改，`workspace.css` 集中工作区样式。
- `table_projection.py` 提供 Case、Scenario 和 Analysis 的通用行列投影；`table_review.py` 承载工作区接口与统一保存。
- `artifact_proposal` 用 `proposal_type` 区分普通修改与流程评审，复用同一个条目 Diff 生成器。区别保留在流程语义中，不再保留两个数据库对象。
- 旧表单编辑器、局部表格编辑器、聊天内 Diff 与接受/拒绝组件删除；聊天保留打开工作区的入口。
- `manual_edits.py` 的证据、行关联与列同步处理并入工作区保存。`native_migration.py` 的早期图检查点恢复逻辑删除。

## 升级边界

停止旧服务，备份原数据目录，解压新版并使用 `python3 start.py --data-dir /原数据目录` 启动。

旧 `review_proposal` 和 `native_revision_proposal` 记录在启动时转换，保留 ID、当前提示与提案内容。项目、资料、Profile、成果版本和历史消息继续保留。

本次输入是源代码压缩包，未包含你的运行数据，因此未检查你机器上的真实检查点。新版不再自动迁移或重放早期 v6/v7 活动任务；这些任务保留已有成果并提示重新开始。当前 v10 图状态仍使用原生恢复。

## 验证范围

最终执行结果见发行包根目录 `RELEASE-MANIFEST.json` 的 `validation` 字段。模型调用使用本地可控响应验证流程，未调用你的内网模型或真实付费服务。本环境浏览器访问本地地址被阻止，浏览器截图及真实浏览器视觉检查未完成；前端交互通过 JSDOM 验证。
