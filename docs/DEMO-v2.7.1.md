# v2.7.1 人工确认模式连续演示

这条路线从上传需求开始，持续操作同一个任务，依次经过“需求理解”“场景”“用例草稿”“评审结果”四个确认节点。确认卡会展示当前成果版本；聊天中的解释、估算、只读评审、覆盖和导出都可以在等待期间进行。

本轮演示应新建任务。已存在的旧任务沿用创建时的暂停约定；不要用旧任务判断 v2.7.1 的四个确认节点是否生效。

## 准备

1. 新建项目与对话，MODE 选择 **Human · 逐步确认**。
2. 上传 `examples/manual-v271/login-requirements.md`，用途选择“需求正文”。
3. 准备好稍后上传的 `examples/manual-v271/forced-logout-change.md`。
4. 确认实际模型可连接。每次只发一条消息，等操作结束后再继续。

后面的“当前成果”指在结果面板打开的成果。需要微调一条记录时，先勾选该条；检查回复中的目标成果与编号，再应用预览。编号由实际生成结果决定，不必与自动化验收中的编号一致。

## 1. 从需求生成开始，采用并编辑澄清建议

发送：

```text
基于上传需求生成测试场景和用例。先澄清会影响设计的缺失规则，在每个关键节点等我确认。
```

预期先出现锁定时长等澄清问题、建议答案及依据。点击“采用全部建议”后检查：已采用的问题从建议列表消失，建议进入可编辑的回答草稿；任务仍在等待，答案尚未提交。

把草稿改成：

```text
连续失败五次后锁定 10 分钟，期满自动解锁。
```

失焦或保存草稿后刷新，修改应保留。点击“保存答案”，再点击“共享到项目”。状态分别显示已保存、已共享；两步都不生成场景。也可以聊天发送：

```text
提交保存这份澄清答案，并共享到项目，先不继续任务。
```

澄清建议是待确认假设。实际模型是否提出同一个问题取决于模型判断；本材料明确保留了锁定时长和解锁方式，现场演示前请预跑。

## 2. 同项目新对话复用已确认事实

保持原任务等待，在同一个项目中新建对话并发送：

```text
本项目已经确认连续失败五次后锁定多久？只回答已确认事实，并说明依据。
```

预期回答“10 分钟，期满自动解锁”，引用刚刚共享的用户澄清。它不能把未提交的原建议当成项目事实。回到原对话，确认原任务仍在澄清节点。

## 3. 确认需求理解后才生成场景

点击“提交并继续”，或发送：

```text
用已保存的澄清继续到需求理解确认。
```

预期到达 **确认需求理解**。查看需求编号、引用、业务图和测试范围，再发送：

```text
解释当前需求理解和测试方案，先不要生成场景。
```

解释后，成果版本与确认节点不变。点击 **确认需求理解，生成场景**，等待 **确认测试场景**。此时应有真实场景成果，还没有生成用例。

## 4. 在场景确认门估算并导出

打开测试场景，发送：

```text
当前场景需要多少条用例？逐场景给出数量区间、拆分理由和假设。只估算，不生成，不继续任务。
```

预期显示估算总区间和逐场景明细，以及所依据的场景版本；用例数量和场景版本不变。随后发送：

```text
把当前场景导出为 Excel，仍停在场景确认。
```

下载并打开文件，检查标题、编号和需求关联。保留这份文件，后面用它对比更新后的导出。此时不要点击场景确认按钮。

## 5. 新资料先只读检查，再定向更新

上传 `forced-logout-change.md`。在资料面板确认它作为业务资料纳入；打开需求理解后发送：

```text
只读分析新附件对已有需求和场景的影响，完整检查新增资料。列出可能受影响的需求及关联场景，不修改成果，不继续任务。
```

预期出现“新增资料影响分析”：登录成功规则及关联场景可能受影响；显示所检查的需求、资料范围和成果版本。原任务仍在场景确认，需求与场景版本不变。

再发送：

```text
按新附件只更新受影响的需求理解及关联场景，明确登录成功后立即注销同账号其他活动会话。无关条目不动，保留当前等待，先不要生成用例。
```

检查受影响的需求与场景各产生一个新版本，带有新附件引用；错误凭证及锁定等无关条目保持原内容。确认卡应刷新到最新场景版本。修改期间确认按钮不可用；旧版本确认请求应被拒绝，不能越过门。

## 6. 生成草稿后暂停，预览场景与用例联动微调

点击 **确认场景，生成用例草稿**。

预期到达 **确认用例草稿**，显示真实用例、步骤、预期结果及覆盖入口。用例应使用刚更新的场景和新资料；尚未自动调用 AI 评审，也没有完成任务。

打开场景，勾选登录成功场景，发送：

```text
微调选中场景为跨设备验证登录后立即注销其他活动会话，并同步它关联的用例。只预览，其他场景和用例不动。
```

预期同一预览包含该场景和关联用例，展示具体修改；预览前后两份成果版本不变，仍在草稿确认。确认目标编号正确后点击“应用此修改”。

检查两份成果各递增一个版本，无关条目逐字段保持不变；用例中的操作明确涉及两台设备，预期明确旧设备会话失效。确认卡绑定最新草稿版本，任务仍等待草稿确认。

## 7. 读真实步骤、只读评审、看覆盖、保存样例

打开用例草稿，依次发送：

```text
展开当前草稿的真实操作步骤和预期结果。
```

```text
只读评审草稿的覆盖、步骤清晰度和预期结果，给出意见。不要优化，不保存修改，不继续任务。
```

```text
查看需求到场景到用例的结构覆盖、缺口和过期状态。
```

检查展示的是已保存用例中的真实步骤，而非凭空补写的新步骤；只读评审有意见且没有保存新用例版本。覆盖应来自当前关联分支及其版本。完整同步后的关系不应显示过期；结构覆盖不代表测试执行通过。

选择一条用例，点击“保存为项目样例”，明确目标 Profile 后保存。也可以发送：

```text
把选中用例的写法保存为当前项目 Profile 的样例。
```

检查 Profile 版本增加，保存的是字段和写法；样例不会成为业务证据。用例版本、草稿确认门及 AI 评审状态不变。

如需演示自定义 Excel 模板，可使用 `examples/conversation-v260/` 中的两份 XLSX，按 `docs/DEMO-v2.7.0.md` 的独立模板 Profile 步骤操作。模板与写法样例属于不同配置；本条最小连续路线使用当前 Profile 导出。

## 8. 明确授权 AI 评审，评审后再次暂停

点击 **确认用例草稿，开始评审**，或发送：

```text
确认当前用例草稿，开始 AI 评审并保存优化结果，评审结果等我最终确认。
```

预期 AI 评审只执行一轮，读取最新草稿，包括刚才应用的跨设备步骤。评审结果保存后进入 **确认评审结果**；当前任务仍未完成。

查看评审意见与当前用例，确认修改有据可查。这里可以继续解释、阅读、微调或导出；完成这些操作不会自动越过最终确认。

## 9. 解释总结、导出最新版本，然后最终确认

在评审结果确认门发送：

```text
解释这次评审结果，列出相关用例编号，用三句话总结新增规则带来的设计变化。不要修改，不要声称测试已经执行。
```

再发送：

```text
分别导出最新场景和当前评审结果为两个 Excel 文件，保留最终确认门。
```

打开两个下载文件，检查最新场景标题、用例标题、操作与预期。重新打开第 4 步的旧文件，其内容应保持原样。解释、总结和导出期间，当前成果版本及确认门都不变。

最后点击 **确认评审结果，完成任务**。若本轮目标显式停在评审，按钮会显示“确认评审，完成任务”，同时将目标扩展到完成。这时原任务才完成，产生结束总结。整个过程仍是同一个原始任务，没有为每次提问重新创建生成任务。

## Auto 对照

另开一个新对话，上传同一需求，选择 **Auto · 自动完成** 并发送“基于上传需求自动生成完整测试场景和用例”。预期仍展示需求理解、场景、用例、评审四阶段成果，正常路径自动完成。未确认规则应在设计假设中明确说明。

## 验收证据与适用范围

自动化入口：

```bash
python -m pytest -q tests/test_manual_journey_v271.py
```

该文件含一条持续的真实 HTTP + LangGraph 人工路径，以及一条 Auto 对照。它从真实上传与主图生成成果开始，检查四门、澄清共享、新资料精确引用、目标条目修改、无关条目保留、覆盖、冻结 Excel 字节及模型调用次数。请求正文只有自然语言、MODE 和 UI 选中成果信息；没有传入 HTTP 命令或任务意图选择器，也不直接修改数据库来制造成果版本或确认状态。

模型响应与路由受控，因此这些测试验证程序执行契约，不证明任意实际模型对每句自然语言都有相同判断。实际模型仍需按本指南预跑。

本环境尝试浏览器演示时，Cloud browser 的 URL 策略拒绝访问本地地址，页面没有加载。因此不把组件测试与 HTTP 测试写成浏览器整条演示已通过；需要在可访问应用的浏览器中执行上述手工检查。
